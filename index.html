SGR: Symbolic-Guided Regeneration

When a large language model repairs or updates a building’s knowledge graph, how do we make sure it does not make things up?

SGR lets the model propose a patch, checks the patched graph against SHACL rules, and feeds every violation back to the model until the graph passes or a reviewer takes over. Every accepted change is recorded with its provenance. The method is evaluated on a clean, fully traced baseline graph of a real building’s HVAC system.

One building, one question

On a summer afternoon one of the chillers on the roof of a research building trips. Facility staff need to know which rooms will get hot, and whom to notify.

With drawings: half a dayFlip through four sheets: the equipment schedule, the system flow diagram, then the HVAC plan and the architectural plan for each floor. The sixth floor alone has 18 fan coil units, and it is easy to miss one.
With a knowledge graph: one queryThe computer follows the arrows: chiller → fan coil units → HVAC zones → rooms. On the 6F graph that returns 13 rooms in under a second: 7 faculty offices, 2 graduate student rooms, 2 academic exchange rooms, 1 laboratory and a lounge. The data room has its own cooling system.

That answer is only as good as the graph.

Drawings are made to build a building, not to run one

Rebuilding the 6F graph from official as-built drawings exposed gaps that are typical of a handover:

  • No room names on the HVAC drawingsEquipment and spaces had to be linked by aligning another drawing by coordinates.
  • No point names or addressesControl drawings give I/O counts, so we know “there is a temperature” but not where to read it.
  • Unclear scopeA “not in this project” remark in the equipment schedule sits between two rows.
  • Copied templatesThe title block of the master index contains text from another project.
  • Mixed periodsThe renovation was split into phases, so data for the same floor come from different times.
  • So errors get inA missing sensor or a wrong arrow sends a query to the wrong room.

Large language models can help repair and update a graph like this, but they can also make things up. SGR lets a model propose repairs while symbolic rules decide what is accepted.

4Check it: SHACL validation

SHACL is the standard way to write rules for a graph, like a building code review. Here are three rules for FCU-6F-10. Press the button to test the graph against them.

    See the three rules written in SHACL 
    # Rule 1: every fan coil unit has a return air temperature point
ex:R1-FCU-RAT  a sh:NodeShape ;
  sh:targetClass  brick:FCU ;
  sh:property [
    sh:path  brick:hasPoint ;
    sh:qualifiedValueShape  [ sh:class brick:Return_Air_Temperature_Sensor ] ;
    sh:qualifiedMinCount  1 ;
    sh:message  "FCU lacks a return air temperature point" ] .

# Rule 2: every fan coil unit is installed somewhere
ex:R2-FCU-Room  a sh:NodeShape ;
  sh:targetClass  brick:FCU ;
  sh:property [
    sh:path  rec:locatedIn ;
    sh:minCount  1 ;
    sh:message  "Equipment has no installed location" ] .

# Rule 3: the zone it supplies contains its room
ex:R3-FCU-ZoneRoom  a sh:NodeShape ;
  sh:targetClass  brick:FCU ;
  sh:sparql [
    sh:message  "Supplied zone does not contain the installed room" ;
    sh:select  """
      SELECT $this WHERE {
        $this brick:feeds ?zone ; rec:locatedIn ?room .
        FILTER NOT EXISTS { ?zone brick:hasPart ?room }
      }""" ] .

    Example shapes for learning. In the real project these run in pySHACL with the Brick 1.4.4 ontology. This page runs the same three checks in JavaScript, so you can try them without installing anything.

    5Repair it

    In SGR an LLM proposes the patch and the rules check it. Here the patch is scripted from the drawing evidence, and nothing changes until you approve it.

    6Passing is not proof

    Rules check that facts fit together, not that they match the building. Record FCU-6F-10 in the wrong room and the wrong room’s zone, then check again. This is why SGR is scored against a clean answer key.

      Quality

      • Passes every SHACL shape shipped with the official Brick 1.4.4. During modelling, the first version produced 55 violations because some relationships were written the wrong way; after correction there were none.
      • An early version contained 26 points filled in to complete the model. After the control drawings were found, all 26 were replaced by drawing-backed points.

      Provenance on every node and relation

      Assertion statusMeaningWhen it is used
      drawing-derivedTaken directly from the as-built drawingsThe sheet and the specific layer, block or text can be named
      inferredReasoned from the drawingsThe drawings point in a direction but cannot confirm it; the reason is stated in the source field
      synthetic-completionSynthetic data added for experimentsCurrently none; any addition is marked separately from original data

      A relation never carries a stronger status than its endpoints: if an endpoint is inferred, every relation to it is inferred too.

      Reproducibility

      • The graph is generated by a build script from the converted drawings; the Turtle file is never edited by hand.
      • Rerunning the script on the same input gives the same SHA-256 hash.
      • Version 1.0 is frozen with its node count, triple count, inferred count and hash recorded. Any correction becomes a new version, and every test that depends on the baseline is rerun.

      Pipeline

      From drawings to a validated, versioned graph, and around the repair loop.

      1. As-built drawingsAutoCAD R14 files covering the equipment schedule, system flow diagram, HVAC and architectural plans, and control schematics.
      2. Local conversionLibreDWG 0.13.3 converts the drawings to JSON or DXF, read in Python. No online viewers or conversion services are used.
      3. Scripted buildA build script produces the Turtle graph and a modelling table; the table records the assertion status of each relation.
      4. FreezeThe baseline is versioned and frozen with its SHA-256 hash.
      5. Graph databaseLoaded into Neo4j 5.26 through n10s 5.26. A round-trip check compares the exported triples with the original file, and any differences are resolved before data taken from Neo4j is validated.
      6. ValidationExported to RDF and checked with pySHACL, using the Brick 1.4.4 ontology and RDFS inference.
      7. SGR repair loopPatch, merge in RDF, revalidate, retry up to K, or escalate.
      8. Record and syncPROV-O provenance is recorded and the passing state is synced back to Neo4j via n10s.

      Evaluation design

      Defects that imitate real handover errors are injected into the clean baseline. SGR then tries to repair them, and the result is compared with the baseline.

      Defect types (examples)

      Injected defectReal situation it imitatesWhat the rules should report
      Delete a fan coil unit’s return air temperature pointHandover data omit a sensorThe unit lacks a return air temperature point
      Delete a fan coil unit’s “located in” relationThe equipment list gives no installed locationThat equipment has no location
      Point a fan coil unit’s “feeds” to another room’s zoneThe floor plan and the system drawing disagreeThe zone does not match the room where the equipment is

      Rules

      • Rule content is set by the supervising researcher, then transcribed into SHACL. Each rule is one sh:NodeShape named with its rule ID, and its rdfs:comment cites the source: a COBie clause, a Brick rule or a drawing number.
      • Every rule passes a positive test (the baseline gives zero violations) and a negative test (a small graph that breaks the rule reports a violation on the right node) before it is frozen with its hash.
      • Shapes use sh:inversePath for relations pointing the other way and sh:qualifiedValueShape to restrict the class being counted.

      Why validation runs in pySHACL

      n10s can validate inside Neo4j, but it supports only part of SHACL, and inverse paths and qualified constraints would need separate testing. SGR experiments therefore always export to RDF and validate with pySHACL, with the Brick ontology and RDFS inference. Without them, subclass checks fail silently.
